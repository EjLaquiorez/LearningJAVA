# 001 — Problem vs Solution

## Objective

Learn to distinguish the **actual problem** from a **proposed solution**. Professional software engineers spend more time understanding the problem than jumping into implementation.

---

# The Core Principle

> **A problem describes what is wrong.**
>
> **A solution describes one possible way to fix it.**

Many beginner developers immediately think about code.

Professional engineers first ask:

> **"What problem are we trying to solve?"**

---

# Why This Matters

Poor software is often the result of solving the wrong problem.

If the problem is misunderstood:

* The wrong software gets built.
* Time and money are wasted.
* Users remain frustrated.
* Teams repeatedly redesign the system.

Understanding the problem is usually more valuable than writing code quickly.

---

# Problem vs Solution

| Problem                                  | Solution                                |
| ---------------------------------------- | --------------------------------------- |
| Customers wait too long to place orders. | Build an online ordering system.        |
| Employees forget their passwords.        | Implement password reset functionality. |
| Inventory counts are inaccurate.         | Introduce barcode scanning.             |
| Managers cannot track sales performance. | Create a reporting dashboard.           |

Notice that multiple solutions can exist for the same problem.

---

# The Iceberg Analogy

Imagine an iceberg.

The visible tip represents the **solution**.

Everything beneath the water represents the **real problem**:

* Business goals
* User needs
* Constraints
* Existing workflow
* Root causes

Professional engineers investigate below the surface before proposing solutions.

---

# A Common Beginner Mistake

A client says:

> "We need a mobile app."

A beginner immediately starts planning screens and writing code.

A professional asks:

* Why do you need a mobile app?
* What problem are users experiencing?
* Who will use it?
* How is the process handled today?
* What outcome are you hoping to achieve?

Sometimes the best solution is **not** a mobile app.

---

# Example

### Client Request

> "Build us an online appointment system."

### Immediate Solution Thinking

"I'll use Java, Spring Boot, and MySQL."

### Engineering Thinking

Ask first:

* What is wrong with the current appointment process?
* Who schedules appointments?
* How many appointments happen each day?
* What causes delays?
* What information needs to be recorded?
* Are appointments ever cancelled or rescheduled?
* Who needs access to the schedule?

Only after understanding these answers should implementation begin.

---

# Mental Model

```
Problem
    ↓
Understand
    ↓
Analyze
    ↓
Identify Root Cause
    ↓
Explore Options
    ↓
Choose the Best Solution
    ↓
Build Software
```

Software development starts with understanding—not coding.

---

# Reflection

When someone asks you to build software, don't ask:

> "How do I build it?"

Instead ask:

> **"What problem are we trying to solve?"**

That single question often leads to better software and better engineering decisions.

---

# Key Takeaways

* Problems and solutions are different.
* Never assume the client's first request is the correct solution.
* Ask questions before proposing technology.
* Focus on understanding the business and its needs.
* Good software engineers solve problems, not just write code.

---

# Summary

The first responsibility of a software engineer is not programming.

It is understanding the problem clearly enough that the chosen solution genuinely helps the people who will use it.

> **Great engineers don't start with code. They start with curiosity.**
